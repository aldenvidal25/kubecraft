Hop-by-Hop Packet Trace: host2 <-> host3
==========================================

Topology reminder:
  host1 (10.1.1.2) -- srl1 (hub) --+-- srl2 -- host2 (10.1.4.2)
                                    +-- srl3 -- host3 (10.1.5.2)

FORWARD PATH: host2 (10.1.4.2) -> host3 (10.1.5.2)
---------------------------------------------------

1. host2 -> default gateway 10.1.4.1 (srl2)
   host2 has no route to 10.1.5.0/24; sends to its default gw.

2. srl2 looks up 10.1.5.0/24 in its routing table
   -> static route: 10.1.5.0/24 via 10.1.2.1 (srl1)
      "host3 subnet via hub"
   Forwarded out ethernet-1/1 toward srl1.

3. srl1 (hub) looks up 10.1.5.0/24
   -> static route: 10.1.5.0/24 via 10.1.3.2 (srl3)
      "host3 subnet via srl3"
   Forwarded out ethernet-1/3 toward srl3.

4. srl3 looks up 10.1.5.0/24
   -> directly connected route (ethernet-1/2, 10.1.5.1/24)
   Delivered directly to host3.

5. host3 (10.1.5.2) receives the packet.

Actual traceroute output (docker exec clab-routing-basics-host2 traceroute 10.1.5.2):
  1  10.1.4.1 (10.1.4.1)  0.842 ms  0.795 ms  0.780 ms   <- srl2
  2  10.1.2.1 (10.1.2.1)  1.257 ms  1.260 ms  1.267 ms   <- srl1
  3  10.1.3.2 (10.1.3.2)  1.637 ms  1.663 ms  1.651 ms   <- srl3 (ingress side, e1-1)
  4  10.1.5.2 (10.1.5.2)  1.086 ms  1.192 ms  1.197 ms   <- host3

Note: hop 3 shows srl3's e1-1 IP (10.1.3.2), the interface facing the
probe source, not e1-2 (10.1.5.1) facing host3. traceroute reports the
interface a hop's ICMP TTL-exceeded reply comes from -- same router,
same path, different IP shown.


RETURN PATH: host3 (10.1.5.2) -> host2 (10.1.4.2)
---------------------------------------------------

1. host3 -> default gateway 10.1.5.1 (srl3)
   host3 has no route to 10.1.4.0/24; sends to its default gw.

2. srl3 looks up 10.1.4.0/24 in its routing table
   -> static route: 10.1.4.0/24 via 10.1.3.1 (srl1)
      "host2 subnet via hub"
   Forwarded out ethernet-1/1 toward srl1.

3. srl1 (hub) looks up 10.1.4.0/24
   -> static route: 10.1.4.0/24 via 10.1.2.2 (srl2)
      "host2 subnet via srl2"
   Forwarded out ethernet-1/2 toward srl2.

4. srl2 looks up 10.1.4.0/24
   -> directly connected route (ethernet-1/2, 10.1.4.1/24)
   Delivered directly to host2.

5. host2 (10.1.4.2) receives the reply.

  2  10.1.3.1 (10.1.3.1)  1.379 ms  1.385 ms  1.378 ms   <- srl1
  3  10.1.2.2 (10.1.2.2)  0.993 ms  1.000 ms  1.004 ms   <- srl2 (e1-1, ingress side)
  4  10.1.4.2 (10.1.4.2)  0.809 ms  0.832 ms  0.858 ms   <- host2


WHY THE RETURN PATH MATTERS
---------------------------------------------------
The forward and return paths both cross the same three routers, in
reverse order, but each direction depends on its own independent set
of static routes:

  Forward:  srl2 -> srl1 -> srl3   (uses srl2's + srl1's + srl3's routes)
  Return:   srl3 -> srl1 -> srl2   (uses srl3's + srl1's + srl2's routes)

If any router is missing the route needed for its direction (e.g. srl1
has a route to 10.1.5.0/24 but not 10.1.4.0/24), the forward packet
arrives fine but the reply gets dropped -- ping reports "100% packet
loss" or a timeout even though the destination actually received the
request. Always check routing tables on BOTH ends of a failed ping.
